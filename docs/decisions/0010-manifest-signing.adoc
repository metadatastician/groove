= ADR 0010: Manifest signing — Ed25519 over canonical JSON, registry-pinned
:date: 2026-07-09
:status: accepted

== Context

Capability spoofing is unmitigated in v0.2: any process can serve a manifest
claiming any capability set (cleave PROOF-NEEDS `G-5` "Manifests
unsigned/untyped on the wire", obligation `O-8` "declared capabilities match
implementation; capability tokens are unspoofable on the wire"). The
LAYERING annex already anticipated a "typed, signable" manifest.

== Decision

. **Scheme** — Ed25519 over a canonical JSON serialisation (the RFC 8785/JCS
  subset sufficient for manifests: UTF-8, lexicographically sorted keys,
  minimal separators, RFC 8259 string escaping; integer-only numbers,
  enforced). Implemented in `cli/src/canonical.rs` + `cli/src/sign.rs`.
. **Wire shape** — a detached `signature` member on the manifest object
  (SPEC §2.1.5): `{alg, public_key, sig, signed_at}`, base64 key and sig.
  The signed payload is the manifest **without** that member. A detached
  member (not an HTTP header) so the signature survives the static-file
  deployment form (SPEC §2.1.4) and any JSON re-serialisation.
. **Trust anchor** — `registry/groove-registry.json` MAY pin `public_key`
  per service. The registry is already the compile-time-embedded single
  source of truth (ADR 0006), which makes it the natural pinning root:
  a pinned service serving an unsigned or mismatching manifest is a failed
  discovery. Without a pin, a valid signature binds the manifest to its key
  but authenticates nothing by itself — stated, not hidden.
. **Producer** — the reference provider signs when `--signing-key` /
  `GROOVE_SIGNING_KEY` (base64 32-byte seed) is set. Burble signing via
  Erlang `:crypto` eddsa is a stretch leg; canonical bytes MUST match this
  implementation (shared test vectors in `canonical.rs`).
. **Verifiers** — `groove validate --verify` (self-consistency + pin);
  probing consumers SHOULD verify pinned services. The gossamer consumer
  leg (`std.crypto.sign.Ed25519`) is Phase 2 and is the remaining O-8 leg,
  tracked in cleave PROOF-NEEDS.

== Consequences

* G-5 moves from "unmitigated" to "design adopted + reference
  implementation"; O-8 is partially discharged (provider + CLI legs).
* The registry schema gains an OPTIONAL `public_key` field
  (`#[serde(default)]` — old registries parse unchanged).
* Key management is deliberately out of scope here: seeds live in
  deployment secrets (env), never in the repo. Rotation = update the
  registry pin (a reviewed change, like any registry edit).

== Amendment (2026-10-08): canonical bytes from ijson-jcs

The Decision's "JCS subset" was looser than it claimed. A differential probe
against `hyperpolymath/ijson-jcs`, the estate's JSON canon (I-JSON, RFC 7493,
plus JCS, RFC 8785), found three gaps in `cli/src/canonical.rs`:

* object keys were sorted by UTF-8 bytes, not by UTF-16 code units
  (RFC 8785 §3.2.3). The two orders agree on ASCII and on every key below
  U+E000, but diverge when a key at U+E000 or above meets a key outside the
  Basic Multilingual Plane;
* integers outside ±(2^53−1) were signed exactly, though they are not
  I-JSON (RFC 7493 §2.2) and other verifiers read them as doubles;
* the verify path parsed with last-wins duplicate keys, so a manifest could
  carry a repeated key that a first-wins consumer reads differently under a
  valid signature (RFC 7493 §2.3).

Amended decision:

. **Canonical bytes** are `ijson_jcs::to_jcs` over the manifest without its
  `signature` member. The crate is a git dependency of `cli/` pinned to a
  commit; the pin moves deliberately, because canonical bytes are part of
  every signature.
. **Integers only, still.** Groove keeps its own guard and refuses any float
  on the sign path before ijson-jcs runs. ijson-jcs would format a double
  per ECMAScript; manifests carry versions, ports and TTLs, so a float in a
  manifest is a mistake, not a value to sign. Integers are bounded to
  ±(2^53−1).
. **Strict parse at verify.** `groove validate --verify` parses with
  `JsonMode::Strict`. A repeated key, an unsafe integer or another I-JSON
  violation is a `critical` `DOG-03-SIG` finding, and the signature, if
  any, is not verified. This holds for unsigned manifests too: the registry pin is
  looked up by `service_id`, so a repeated `service_id` would otherwise
  choose which pin applies.

Compatibility: the canonical bytes are unchanged for every manifest that is
I-JSON (integers within ±(2^53−1), no noncharacter such as U+FFFE in any
string) and has no object holding both a key with a code point in
U+E000–U+FFFF and a key outside the Basic Multilingual Plane. Measured
2026-10-08 over 59 files (58 JSON files under `.well-known/groove`
directories in the local estate checkouts, plus `examples/minimal-manifest.json`;
two non-JSON files in those directories were skipped): all 59 canonicalise
to identical bytes under the old and new code, and all 59 are I-JSON, so
the Strict parse refuses none of them. Manifests outside that set were
not measured. A manifest previously signed with an integer beyond the bound
or a noncharacter no longer verifies, and must be re-signed without it; one
signed with keys in the diverging ranges no longer verifies either, and
must be re-signed.

Burble's stretch leg must match these bytes. The shared test vectors in
`canonical.rs` now include a UTF-16 key-order vector, the ±(2^53−1)
bound and a noncharacter refusal.

== Amendment (2026-10-09): Strict parse at Check 1

The 2026-10-08 amendment put the Strict parse in `--verify` only. Plain
`groove validate`, `groove probe` and `groove mesh` still parsed last-wins,
so the I-JSON rule held only when someone asked for verification, and a
manifest with a repeated `service_id` was listed by `probe` under its last
value.

Amended decision, superseding point 3 above:

. **Check 1 parses Strict.** `validate_manifest_content` parses the
  manifest with `ijson_jcs::JsonMode::Strict`. A repeated key, an integer
  outside ±(2^53−1) or another I-JSON violation is a `critical` `DOG-03`
  finding on every `groove validate` run, with or without `--verify`, and
  no other check runs on that manifest.
. **Verify reports nothing on a manifest Check 1 refused.**
  `verify_signature_finding` uses the same Strict parse and returns no
  finding when it fails, so `groove validate --verify` reports such a
  manifest once, as `DOG-03`, and never as merely unsigned. Its signature
  and registry pin are not checked. The `DOG-03-SIG` finding for a
  manifest that is not I-JSON is retired.
. **`probe` and `mesh` parse Strict.** A probed manifest that is not
  I-JSON is left out of the listing, as one that is not JSON was before.

Not covered: the reference provider (`provider/`) parses the bodies it is
sent and its `--manifest` file last-wins before it calls
`validate_manifest_content`, so a repeated key there has already collapsed
when Check 1 sees it.
