## Pins and official lock generation

The scanner retains full SHA `b8f60511e76c9015d86990317162dce653c92fe1`.
It was runtime-proven by enaction-engine run `42367280154` before this change.
The callee declares no secrets and needs only `contents: read`; the caller passes
none. No permission or secret expansion was needed for the scanners.

The old safety job used official `gh-actions-lock v0.1.6` against a v0.0.3 lock.
Its older output was not adopted. CI now uses official `v0.4.1` for both
`--verify-local` and network/provenance `--verify`.

The checked-in lock is the unedited output of official `gh actions-lock v0.4.1`
in [run 42520184417](https://github.com/metadatastician/groove/actions/runs/42520184417).
Because this workspace cannot download GitHub release assets or Actions logs,
the temporary read-only workflow exported the generated bytes through check-run
annotations (base64 transport only). That workflow was removed afterward.
The existing lock was the input; floating action refs were not deliberately bumped.

The tool canonicalizes SHA-backed action entries to their tagged-release entries
and does not lock cross-repository `jobs.<id>.uses` reusable workflows
([upstream limitation #179](https://github.com/github/gh-actions-lock/issues/179)).
Its generated empty scanner workflow section is therefore expected, not a promise
of transitive scanner locking. Scanner safety relies on the source full-SHA pin
and actual runtime acceptance. Full-SHA source refs, including CodeQL, are preserved;
verification's suggestion to replace bare SHAs with tags is intentionally not applied.
Run `42520184417` restored the SHA-bearing source files after generation and then
passed both verification modes against those preserved sources.
